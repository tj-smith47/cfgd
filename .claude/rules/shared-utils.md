# cfgd Shared Utilities — `cfgd-core/src/util/`

Cross-cutting functions used by multiple modules live in `cfgd-core/src/util/<topic>.rs` and are re-exported through `cfgd-core/src/lib.rs` so external callers reach them as `cfgd_core::<name>(...)`. **Before writing any helper function, check the topic file first** — if a similar function exists, use it. If a new function will be needed by more than one module, add it to the topic file that matches its domain (or to a new topic file if none fits cleanly).

External call sites do not change: `cfgd_core::utc_now_iso8601(...)`, `cfgd_core::sha256_hex(...)`, `cfgd_core::atomic_write(...)`, etc. — the topic-file split is a layout change, not an API change.

## Constants

- `API_VERSION` — canonical API version string (`cfgd.io/v1alpha1`); use everywhere instead of string literals
- `CSI_DRIVER_NAME` — canonical CSI driver name string (`csi.cfgd.io`)
- `MODULES_ANNOTATION` — canonical annotation key (`cfgd.io/modules`)
- `LABEL_MACHINE_CONFIG` — k8s label key (`cfgd.io/machine-config`); use instead of the raw string in gateway/controllers
- `LABEL_DEVICE_ID` — k8s label key (`cfgd.io/device-id`); use instead of the raw string in gateway/controllers
- `OCI_ANNOTATION_PLATFORM` — OCI manifest annotation key (`cfgd.io/platform`); use instead of the raw string in oci.rs
- `PROFILE_SCRIPT_TIMEOUT` — 5 minutes; use instead of hardcoded `Duration::from_secs(300)`
- `COMMAND_TIMEOUT` — 2 minutes, for external commands
- `GIT_NETWORK_TIMEOUT` — 5 minutes, for git network operations
- `DURATION_BUCKETS_SHORT` / `DURATION_BUCKETS_LONG` — Prometheus histogram bucket presets

## Time

- `utc_now_iso8601()` — ISO 8601 timestamp (the only timestamp function; do NOT create wrappers)
- `unix_secs_now()` — current Unix epoch seconds
- `unix_secs_to_iso8601(secs)` — Unix epoch to ISO 8601
- `iso8601_to_filename_safe(ts)` — strip `:`, `-`, `T`, `Z` from an ISO 8601 timestamp so it can be used as a path segment; use instead of inline `.replace([':', '-', 'T', 'Z'], "")`
- `utc_now_filename_safe()` — convenience: current UTC time as a filename-safe string (composes the two above)
- `BACKUP_TIMESTAMP_FORMAT` — the `strftime` shape of a `spec.backups[]` snapshot stamp (`%Y%m%dT%H%M%SZ`)
- `unix_secs_to_backup_stamp(secs)` — render a Unix timestamp in `BACKUP_TIMESTAMP_FORMAT` (`20260512T143025Z`)
- `utc_now_backup_stamp()` — convenience: current UTC time in `BACKUP_TIMESTAMP_FORMAT`; the `{timestamp}` `namePattern` variable
- `parse_duration_str(s)` — parse "30s", "5m", "1h", or plain seconds into `Duration`
- `humanize_age_since(ts, now)` — render an ISO 8601 timestamp's age relative to `now` as `"just now"` / `"Nm ago"` / `"Nh ago"` / `"Nd ago"`; `None` when `ts` fails to parse or is after `now` (clock skew). Both `ts` and `now` are plain `&str` — the `cfgd` binary crate holds no `chrono` type of its own and depends only on the ISO 8601 strings `cfgd-core` already hands back — and `now` is a caller-supplied parameter rather than a wall-clock read, so a render can be pinned in a test/golden. Used by `cfgd status`'s recorded-state header to show how stale the last live scan is (`StateStore::last_scan_at`)
- `is_stale_since(ts, now, threshold_secs)` — whether `ts` is more than `threshold_secs` older than `now`; an unparseable `ts` (or `now`) reads as stale rather than silently fresh, since a caller deciding whether to show a "this is old" hint must not suppress it over a malformed record. Shares its parse-and-diff primitive with `humanize_age_since` so the two can never disagree about one timestamp's age. Used by `cfgd status`'s recorded-state header to decide whether to hint at `--scan` (threshold: `cfgd_core::daemon::DEFAULT_RECONCILE_SECS`)

## CLI parsing / validation

- `parse_env_var(input)` — parse `KEY=VALUE` into `EnvVar`; validates via `validate_env_var_user_name`
- `parse_alias(input)` — parse `name=command` into `ShellAlias`; validates via `validate_alias_name`
- `validate_env_var_user_name(name)` — validates shell-safety + rejects reserved `CFGD_*` prefix; use for all user-supplied env var names
- `validate_env_var_name(name)` — matches `[A-Za-z_][A-Za-z0-9_]*`; prevents shell injection (low-level; prefer `validate_env_var_user_name` for user input)
- `validate_alias_name(name)` — matches `[A-Za-z0-9_.-]+`; prevents shell injection
- `shell_escape_value(value)` — escape a value for shell `export` statements
- `xml_escape(s)` — escape `&<>"'` for safe XML/plist inclusion
- `escape_control_chars(s)` — render C0/C1 control characters as visible `\xNN`; use on any untrusted string shown on the terminal before the user acts on it (module review/diff surfaces). A raw `\r` or `\x1b[2K` in a module-supplied value otherwise repaints or erases the lines describing it, so the user approves something other than what they read. Escapes rather than strips, so the value's true length and shape stay visible
- `sanitize_k8s_name(name)` — RFC 1123 DNS label sanitization
- `manager_family(manager)` in `cfgd-core/src/util/strings.rs`, re-exported as `cfgd_core::manager_family` — the ONE mapping from a registered package-manager name to the family it belongs to: everything before the first `-`, so `brew`, `brew-tap` and `brew-cask` all answer `brew`. It exists because three registered managers can be ONE binary and one prefix: a sub-manager has no bootstrap of its own, answers `is_available()` with its parent's, and is stranded by its parent's removal, so any surface enforcing mutual exclusion or pairing an install with a bootstrap has to collapse the family or it is reasoning about three independent things that are one. Three call sites depend on that agreement: the planner pairing a sub-manager's install with its parent's bootstrap and the CLI's stranded-install warning (both `crates/cfgd/src/cli/plan_ops.rs`), the bootstrap-in-flight check in `crates/cfgd/src/packages/mod.rs`, and `Slot::lane` in `crates/cfgd-core/src/reconciler/lanes.rs`, whose lane key MUST be the family — keyed on the name, the concurrent `Packages` dispatch runs three `brew` processes at once, which is exactly what one-operation-per-manager exists to prevent. The one action whose lane is NOT its own manager's family is a `ManagerAction::Provision`, which lanes on its `via`'s family: the command that runs is the mediator's (`provision npm via apt` is an `apt-get install`), and two provisions mediated by one system manager laned on their own names hold that manager's lock against each other. Deliberately NOT applied anywhere the manager is named rather than serialized: the phase tree's action subjects, the journal's `resource_id` and every other persisted or `-o json` string, and the availability sub-gate (`Slot::drains`, which asks the registry whether a manager needs bootstrapping) all keep the REGISTERED name, because those surfaces have to say the manager the user declared and `brew-cask` is not `brew`. The one display exception is the blocked-action wait bar, which names the lane on purpose — an action held back by a running `brew` is waiting on brew, and saying `waiting on brew-cask` would name something that is not in the way
- `load_config_and_profile_module_scoped(cli, printer, module_filter, with_profile)` in `crates/cfgd/src/cli/helpers.rs` — the `--module` isolate shared by `cmd_apply` and `cmd_plan`: loads (and drains) `cli.config` EXACTLY ONCE. When `module_filter` names one or more modules and `with_profile` is `false`, the run is ISOLATED from the active profile unconditionally — a profile is never even resolved, so a profile that DOES resolve cannot leak its packages/files/env/aliases/system/scripts into a run the caller asked to isolate. `--module --with-profile` (or no `--module` at all) behaves exactly like a normal run: the active profile must resolve, same as `cfgd apply` with no flags. Replaces a duplicated load-drain-fallback block that previously drained the same file's deprecation notices twice per `apply --module x` / `plan --module x` invocation
- `TokenHits` + `warn_zero_match_tokens(plan, flag, hits, owners_present, known_modules)` in `crates/cfgd/src/cli/plan_ops.rs` — the SSOT per-token match accounting for `filter_plan`'s `--skip`/`--only` tokens, and the only place either produces a "matched no actions" message. `TokenHits` starts every supplied token at zero and increments per action it prunes, so a token shadowed entirely by an earlier one is still reported as a miss — silence is never mistaken for coverage; `.misses()` reads back the tokens that stayed at zero. `warn_zero_match_tokens` renders each miss as `` `--{flag} {token}` matched no actions in this plan``, escaping the token through `escape_control_chars` first (it is untrusted terminal input echoed verbatim), with a hint appended: `--module <name>` when the token is a `module:<name>` naming a module cfgd knows about but that isn't part of this run's graph (`module_known_but_unresolved`, a pure `HashSet` lookup), else the owner tokens the plan actually held, when any are. `known_module_names(config_dir)` is the ONE read of the module tree and lockfile behind that lookup — computed once by `filter_plan`'s caller (`apply.rs`/`plan.rs`), and only when `--skip`/`--only` is actually supplied, rather than threading `config_dir` itself through `filter_plan` and re-reading disk once per missed token (the shape ~30 test call sites carried before this was closed). Pushed into [`reconciler::Plan::warnings`] rather than printed directly — the same route the undecidable-package-batch warning (`UndecidableBatch::warning()`, `reconciler/pending.rs`) already takes — so there is one producer, one render (`reconciler::ApplyRun::header`, via `printer.alert` so it stays visible at any depth and any verbosity), and one serialization (`build_plan_output`'s `warnings` field), and a `-o json` consumer sees the same miss a human reading the header does instead of an empty `phases` array with no explanation. `filter_plan`'s `bool` return (whether anything missed) folds into `ScopeReport.filter_miss`, so `report_no_in_scope_actions` can tell "a filter never matched anything" apart from "the machine converged"
- `RunContext` in `crates/cfgd/src/cli/run_context.rs` — the per-invocation holder of everything a run must build AT MOST ONCE: the parsed config, the resolved profile, the state store, the config-free provider registry and the run's `ManifestCache`. A `cmd_*` builds one at its top (`RunContext::new(cli, printer)`, pure — it copies two references and derives the config dir) and threads `&ctx` into `compose_with_sources` / `resolve_desired_state` / `withheld_for_run`; every slot is a `OnceCell` filled on first ask, so a command that never wants the state store still never opens one. `config()` drains the config's deprecation notices exactly once and `active_profile_name()` deliberately does NOT — the parse and the drain are separate steps, because a module-only path needs the active profile's NAME and must not start printing notices it never printed. `state_opt()` is the advisory read for a path that records if it can. `base_registry()` is the config-FREE registry a module-only path wants; a composing path takes `DesiredState::take_registry(cfg)`, the config-aware one `resolve_desired_state` hands back, instead of building a second identical one — the field behind it is a `OnceCell` the resolution fills only when it has modules to map, so a module-free composition builds no registry at all and the first caller to ask builds it. Not `Sync` by construction — concurrent phases receive the resolved objects (`&StateStore`, `&ProviderRegistry`), never the context. Scoped to one run and never process-global, so a daemon can hold one per tick
- `ManifestCache` + `resolve_manifest_packages_cached(spec, config_dir, cache)` in `crates/cfgd/src/packages/mod.rs` — the manifest-reading half of the above, reached through `ctx.resolve_manifest_packages(spec)`. `resolve_manifest_packages` runs twice on a `status` / `diff` / `plan` invocation (once over the composed profile, once over the local-only profile the source-decision scope is classified against) and both passes parsed the SAME Brewfile, `package.json` and `Cargo.toml` off disk. Entries are keyed by file path + manifest kind and carry the file's `(mtime, len)`, so a manifest a lifecycle hook rewrote mid-run is re-read rather than merged stale. Deliberately not process-global: a manifest is only stable for the length of one run. `resolve_manifest_packages` (uncached) stays for the single-pass callers and is a fresh-cache delegate
- `Platform::current()` in `cfgd-core/src/platform/mod.rs` — the ONE platform detection per process, and what every production reader takes. `Platform::detect()` spawns `sw_vers` on macOS and `freebsd-version` on FreeBSD and reads `/etc/os-release` on Linux, and it was being paid per file manager, per module walk and per daemon tick. No invalidation counterpart because none of its inputs can change under a running process; `detect()` stays public for the detection unit tests and for the memo itself
- `http_agent(timeout)` in `cfgd-core/src/http.rs` — the ONE `ureq::Agent` per distinct timeout, keyed by the five named `HTTP_*_TIMEOUT` constants. An `Agent` OWNS its connection pool, so a per-call agent threw away its pooled TLS connections on drop and an OCI push of N layers paid a full TCP + TLS handshake per request to the same host; `Agent::clone` is allocation-free, so handing out a clone costs a refcount bump. A caller needing a genuinely different agent shape (a proxy, a client certificate) builds its own rather than widening the key — two agents differing in anything but timeout are not interchangeable
- `format_bytes(bytes)` in `cfgd-core/src/util/strings.rs`, re-exported as `cfgd_core::format_bytes` — the workspace's ONE human byte-size renderer (`512 B` / `1.5 KB` / `50.0 MB`). Used by `upgrade` (release asset size), `backup list --snapshots` (snapshot size) and `backup::report_backup_record` (the snapshot line's size detail); never hand-roll a second scale in a command. It lives in core rather than in the CLI because `report_backup_record` does, and a core renderer cannot call a `pub(in crate::cli)` helper
- `Theme::arrow(&self) -> &str` in `cfgd-core/src/output/theme.rs`, and `Printer::arrow(&self) -> &str` in `cfgd-core/src/output/printer.rs` (a thin delegate to the same field) — the ONE arrow glyph for a rendered `old -> new` / `source -> target` relationship (`icon_arrow`, `"→"` by default, themeable per preset/config). A caller composing such a string interpolates `printer.arrow()` instead of hardcoding ASCII `->` or a bare Unicode `→` literal, so a theme override applies uniformly rather than leaving some relationships themed and others not. A pure `Doc`-building function with no `Printer` in scope (`build_module_show_doc`, `modules::diff_module_specs`, `build_compliance_diff_doc`) takes an `arrow: &str` parameter instead, with its sole caller passing `printer.arrow()` — the same thread-it-through shape `condense_action_desc_for_display` uses for a value only the CLI boundary can supply. A REVERSED relationship (`X resolved/sourced from Y`) is never rendered with a mirrored arrow glyph; it is reworded with the plain word "from" instead, so the single canonical glyph stays reserved for genuine left-to-right transitions. `reconciler/format.rs::provenance_suffix`'s `" <- {origin}"` is the one exception, and stays ASCII deliberately: it is a PERSISTED string (`managed_resources` id, journal `resource_id`, `-o json` payload), and persisted/matched strings never change shape for a display migration
- `Absence` (`NotInstalled` / `Missing` / `NotFound`) in `cfgd-core/src/util/strings.rs`, re-exported as `cfgd_core::Absence` — the ONE absence vocabulary, so three call sites naming the same kind of gap can't drift into three different spellings. The choice is about WHAT is absent, not how badly: `NotInstalled` — could exist on this machine, a manager reports it doesn't (`doctor`'s package/provider/manager rows, `live_drift`'s `ManagerDriftPhrase`, `compliance`'s package check); `Missing` — the user's own config DECLARED it and it isn't on disk (`diff`'s package-drift qualifier and its persisted `shape` field, `compliance`'s file/secret checks); `NotFound` — a LOOKUP came back empty, searching a registry or resolving a name that matches nothing (`diff`'s unknown-module message, `doctor`'s config/git/sops/manager rows, `module registry`'s module/registry lookups). `Display` renders the bare word for interpolation into a longer sentence (`format!("{}; run 'cfgd init' to generate", Absence::NotFound)`); `.as_str()` hands back the `&'static str` directly where a `.qualifier(...)`/`.detail(...)` call takes one. A fourth spelling in the same family but a DIFFERENT question ("not cached" — a source cache miss, not "does this exist") stays outside the enum on purpose; widening it to catch every absence-shaped phrase in the workspace would blur the three questions it exists to keep separate. **Two of the listed consumers turn the display literal into a WIRE value**: `diff`'s persisted `-o json` `shape` field and `compliance`'s hashed snapshot `detail` field (`snapshot_content_hash` digests it to decide whether a machine changed). `absence_literals_are_a_pinned_wire_contract` in `util/strings.rs`'s own test module pins the three literals byte-for-byte for exactly this reason — a display reword that touches `as_str()` must update that test on purpose and audit both consumers, not land as an incidental find-and-replace
- **Owner-carrying composers** in `cfgd-core/src/output/` — every render surface that names a `kind:name` owner (`module:nvim`, `source:acme`) styled through `OwnerLabel`'s three slots, instead of a hand-built `format!("{kind}:{name}")` string folded into a single coat. Reach for the one matching the call site's shape rather than hand-composing a new one:
  - `Printer::heading_owner_prefixed(prefix, &OwnerLabel)` — a top-level `<Verb> <owner>` heading (`Add source:acme`); `Doc::heading_owner(&OwnerLabel)` is the buffered-`Doc` counterpart. Named `_prefixed` on the streaming side, not plain `heading_owner`: the two used to share that name over incompatible first arguments (a leading verb here, `kind` there), so a call site four files from its sibling read as if it did the same thing
  - `Printer::section_owner(&OwnerLabel)` / `Printer::section_owner_or_collapse(&OwnerLabel)` — a top-level section headed by the owner token; `_or_collapse` leaves no trace when nothing renders inside it (for a caller that cannot know whether the owner has anything to say until after it has said it)
  - `SectionGuard::section_owner(&OwnerLabel)` / `.section_owner_or_collapse(&OwnerLabel)` — the same pair, nested: opens an owner-headed section inside a section already open
  - `Doc::subsection_owner(&OwnerLabel, build)`, backed by the private `SectionBuilder::new_owner` — the buffered-`Doc` counterpart of a nested owner section
  A site needing an owner-carrying variant the composer surface lacks gets one added here, cataloged in the same commit — see `output-module.md`'s Printer method list for the streaming-vs-buffered pairing of each
- `Printer::command_list(pairs)` / `SectionGuard::command_list(pairs)` / `Doc::command_list(pairs)` / `SectionBuilder::command_list(pairs)` in `cfgd-core/src/output/` — a "command — description" list, `kv_block`'s counterpart for a left column that is a shell command rather than a data-carrying key (the first-run "Next Steps" banner in `cfgd init` / `cfgd enroll`). Its key column carries no `KEY_WIDTH_CAP`: `kv_block` wraps a key past 24 chars onto its own line with the value indented beneath it, which is correct for an arbitrary fact but severs the glue that makes a command list scannable the moment one command runs long — two of three `cfgd init` rows and one of four `cfgd enroll` rows are past the cap. The glue is the canonical `" — "` em-dash a status subject/detail pair already renders with, never `kv_block`'s plain whitespace gap, because this is a list of DESCRIPTIONS rather than a list of VALUES. `KEY_WIDTH_CAP` itself stays untouched — widening it globally would only move the wrap point, not remove it, and would change every unrelated `kv_block` render in the product for one banner's sake
- `AccentHeading` in `cfgd-core/src/output/accent_heading.rs` (`pub(super)`, `plain()`/`styled()`) — the ONE composer for the "Caveats" section heading (`Printer::section_caveats`), painted `theme.accent`, unstyled of bold — the phase-name slot, no `.bold()` since bold never pairs with a colour-bearing slot. Replaces a hand-composed `accent.apply_to("Caveats")` call. Deliberately does NOT route through `PhaseLabel`: "Caveats" is not a phase, and `PhaseLabel` would render `Phase: Caveats`. No external caller reaches it today (`pub(super)`), so it stays cataloged here for the reasoning rather than for a second call site to copy
- `Printer::narrate(running, |sp| work)` in `cfgd-core/src/output/printer.rs` — the ONE way a long wait is narrated, and the settle-safe form of `printer.spinner` + inner-fn + match-once. It opens a spinner labelled `running`, hands `work` the live `&mut Spinner` so each step renames the line through `set_message` (the manager being enumerated, the pass being run, the probe being taken — real state, never decoration), and matches ONCE on the result: success retires the bar SILENTLY, failure settles `Role::Fail` at whatever step `set_message` last named. Silence on success is the contract, not an omission — narration is live-region-only, so a successful run's permanent output stays byte-identical to the same run before the spinner existed and every golden in the suite stays a golden; a site wanting an outcome line writes it itself afterwards (`backup`'s snapshot row, `restore`'s status line), reaching for `Spinner::finish_silent` where it builds the bar by hand. The failure settle carries NO detail: the `Err` it returns is rendered at the CLI boundary a moment later, and a detail here would print the same error twice. Never hand-roll the shape at a call site — the reason it exists is that a spinner opened by hand and hit by an early `?` between creation and its matching finish is abandoned to `Drop`, which can only report the generic `(interrupted)`. Narrated through the OWNING printer wherever a command derives a Quiet printer for its library work (`cli/compliance.rs`, `cli/source/show.rs`), so `Quiet` and `-o json` suppress the wait per policy and the structured channel stays pure. Current sites: the whole live drift scan (`cli/live_drift.rs`), per-manager package enumeration on a memo MISS (`providers/mod.rs`), `status --scan --module` (`cli/status.rs`), `compliance`'s snapshot collection, `verify`'s four passes, `doctor`'s probe groups, `generate`'s AI round-trip and `--scan-only` scans, `backup run`/`backup restore`, `upgrade`'s install tail and `source show`'s cached load
- `pluralize(count, noun)` / `plural_noun(count, noun)` / `agreeing_verb(count, verb)` in `cfgd-core/src/util/strings.rs`, re-exported as `cfgd_core::pluralize` etc. — the ONE agreement rendering for a counted sentence, and what every count-carrying line reads from (`22 actions succeeded`, `1 action succeeded`). `pluralize` renders count + noun; `plural_noun` is the noun alone for a sentence that NAMES the things rather than counting them (`referenced by profiles: work, home`); `agreeing_verb` is the third-person singular the count calls for, and exists because a line that pluralizes only its noun renders `1 non-file action require manual review` — worse than the `N action(s)` it replaced. Regular English only: a noun whose plural is not `+s`, and `be`/`have`, get spelled out at the call site
- `action_display_subject(action)` in `crates/cfgd-core/src/reconciler/format.rs`, re-exported as `cfgd_core::reconciler::action_display_subject` — the ONE display derivation of an action's subject, returning a `DisplaySubject { marker, body }` that renders as `<marker>: <body>` (marker `None` for every kind but a script, whose marker the status renderer styles separately). Every display site reads from it and none derives its own: `render_plan_tree` (the preview bullet), `align_width` (the phase's alignment column) and `apply.rs`'s per-action subjects map (the executed status line) — three strings that must be identical, because a shorter executed subject mis-pads every trailing field in the phase and a preview naming a different string than the execution is a lie about what ran. Four partial views exist in the same file for callers that hold a script's parts rather than an `&Action`. Two are for the apply paths, and condense the BODY before appending the provenance suffix so a long or multi-line body cannot truncate away the source that delivered it: `script_run_subject(run, phase, origin)` (profile scripts, via `scripts_apply.rs`) and `module_script_subject(run, phase, origin)` (module hooks, via `modules.rs`). Two more are for scripts that run OUTSIDE a plan and so carry no origin: `hook_script_subject(marker, run)` (marker + condensed body) is the one every hook context reaches — the daemon's `onDrift`, apply's `onChange` and the backup engine's `preBackup`/`postBackup` all carry their marker — while `bare_script_subject(run)` (condensed body alone) is the marker-less sibling behind `ScriptSubject::Bare`, whose production reach is a module package's `run:` installer script (`reconciler/modules.rs`). Both are the ONE derivation shared by `ScriptStatus::new` in `reconciler/scripts.rs`, which composes the status line as each script finishes, and by the caller that opens the pseudo-phase and must size its alignment column with `align_width_of` BEFORE the first script runs — two copies of the format string mis-pad every line in the group the moment either moves, so never rebuild `"{marker}: {body}"` by hand (`DisplaySubject`'s own `Display` already is it). Never persist a `DisplaySubject`: the `managed_resources` id, journal `resource_id`, `ActionResult.description` and the `-o json` plan payload come from `format_action_description` / `format_plan_item` and stay byte-identical to the source body
- `condense_action_desc_for_display(action, desc)` in the same file — the narrower gate for a raw description string that is NOT an action subject. It condenses (via `condense_script_label`) only the two arms embedding a raw `run_str()` body — `Action::Script` and `Action::Module` + `ModuleActionKind::RunScript` — and returns every other description untouched. Reach for it when you hold a `desc` rather than a subject: the pre-script abort message and the subjects-map fallback in `apply.rs`. For anything the tree renders, call `action_display_subject` instead. It lives outside `util/` deliberately, because it takes an `&Action` and `util/` must not depend on `reconciler` types. Never apply it to the value you persist, for the same reason
- `system_resource_key(configurator, key)` in the same file, re-exported as `cfgd_core::reconciler::system_resource_key` — the ONE composition of a system setting's `<configurator>.<key>` identity, and the only way to build it. Three surfaces mint this string and match it against each other, so a byte of divergence between any two records drift that is never resolved: `format_action_description` (the `managed_resources` id and the journal `resource_id`), `cli::live_drift` (the `drift_events` id `resolve_drift` must find) and `compliance::collect_system_checks` (the check key `compliance diff` pairs two snapshots on). It carries a `debug_assert` that the `SystemDrift::key` does not open with its own configurator's name — six configurators once self-prefixed, doubling the name into two PERSISTED columns, and undoing that cost a state migration
- `system_key_doubling_error(configurator, key) -> Option<String>` in the same file, re-exported as `cfgd_core::reconciler::system_key_doubling_error` — the ONE statement of that rule and of its diagnostic, so the two sites enforcing it cannot disagree about what counts as doubled or about what to say. cfgd-core enforces it debug-only, inside `system_resource_key` and from the planner (`reconciler/plan.rs`), where a configurator's `diff` output first meets its name and so every configurator is checked on every planning run rather than only the ones a test pins — debug-only on purpose, because a doubled key still composes a usable id and a release build must not panic mid-apply over a naming defect. `cfgd::system::assert_keys_undoubled` enforces the same predicate unconditionally against each configurator's own diff fixture. Never restate the `starts_with` check or the message at a third site
- `compliance::snapshot_content_hash(snapshot)` in `crates/cfgd-core/src/compliance/mod.rs` — the ONE serialize-and-digest derivation for a compliance snapshot, returning `(json, digest)`. `StateStore::store_compliance_snapshot` derives from it internally rather than accepting a hash, so `compliance_snapshots.content_hash` always describes the `snapshot_json` beside it. Both writers (the daemon's reconcile tick and `cfgd compliance`) take their change-detection hash from here; they previously hashed different serializations of the same snapshot, so a tick following a CLI run always read "changed". The digest is NOT of the stored bytes: `snapshot_json_content_hash(json)` — the shared half, also registered as the migration's `cfgd_compliance_content_hash` scalar — drops `VOLATILE_SNAPSHOT_FIELDS` (the collection timestamp) and re-serializes canonically before hashing, because the detector's whole job is telling an unchanged machine from a changed one and a timestamp in the digest makes every tick look changed

## Shell quoting (generated shell files)

Quoting is per-dialect: bash/zsh double quotes, fish single quotes and PowerShell single/double quotes each honour a different escape mechanism, so there is no one correct escaper. Every one of the `*_quoted` helpers returns the COMPLETE token **including its surrounding quotes** — that is the point. A generator arm that interpolates a bare value into `alias {}={}` or `Set-Alias -Name {} -Value {}` is how a module-supplied value became executable at shell startup; taking the quotes from the helper makes that shape impossible to write by accident.

- `posix_double_quoted(value)` — a complete `"…"` token for bash/zsh
- `escape_double_quoted(s)` — the BODY of the above, for the rare caller that must join escaped fragments inside one pair of quotes (e.g. `"a:b:$PATH"`). Escapes `\`, `"`, `` ` ``, and escapes `$` **unless** it opens a plain `$NAME` / `${NAME}` parameter reference — so a declared `/opt/bin:$PATH` still expands, while `$(cmd)`, `$((…))`, `${x:-…}`, `${x@P}`, `${!x}` all become literal. `!` is deliberately not escaped: history expansion never applies to a sourced file, so `\!` would corrupt the value with a literal backslash
- `posix_single_quoted(value)` — a complete `'…'` token for POSIX sh; an embedded `'` is re-supplied via the classic `'\''` close/escape/reopen idiom and everything else survives byte-for-byte. Also the correct quoting for a systemd `environment.d` assignment, which accepts the same idiom — without it a newline in a value ends the assignment and the remainder stands as further assignments in the user's session environment. It cannot suppress `$NAME` / `${NAME}`, which systemd expands after parsing regardless of quoting
- `fish_single_quoted(value)` — a complete `'…'` token for fish; escapes `'` and `\`, the only two escapes fish honours inside single quotes (leaving a trailing `\` unescaped ends the quoted region early)
- `powershell_single_quoted(value)` — a complete `'…'` token for PowerShell; `''` is the only escape and the contents are fully literal. The default choice for PowerShell
- `powershell_double_quoted(value)` — a complete `"…"` token for the one PowerShell case that must interpolate (`$env:` references in a declared value)
- `escape_powershell_double_quoted(s)` — the BODY of the above; backtick-escapes `` ` ``, `"`, and `$` unless it opens a `$NAME` / `$env:NAME` / `${env:NAME}` reference, so `$(…)` subexpressions cannot run
- `cmd_double_quoted(value)` — a complete `"…"` token for `cmd.exe`/batch. Doubles every `%` to `%%`, the batch-parser escape for a literal percent (whether a `cmd.exe /C <string>` invocation collapses `%%` the same way a `.cmd` file body does is unverified — it needs a real Windows host) — `%` is a legal NTFS filename character and `cmd.exe` expands `%NAME%` even inside double quotes, so an unescaped wrap can splice the caller's own environment into the value. `"` is not escaped: NTFS forbids the character in a filename

A PowerShell function-wrapper alias must carry its command as a quoted string built into a script block at CALL time (`function n { & ([scriptblock]::Create('<cmd> @args')) @args }`); pasted between the braces directly, a `}` in the command closes the function early and the remainder runs while the profile is still loading.

## Filesystem

- `default_config_dir()` — cross-platform config dir (Unix `~/.config/cfgd`, Windows `AppData\Roaming\cfgd`)
- `expand_tilde(path)` — expand `~/...` or `~\...` to home; uses `HOME` on Unix, `USERPROFILE` (then `HOME`) on Windows
- `absolutize_path(path)` — resolve `path` to an absolute path LEXICALLY (CWD-join + `.` removal, via `std::path::absolute`) without requiring it to exist and without following symlinks; use for any CLI entry point (`--config`) that must become absolute at the boundary. Deliberately does not canonicalize — a symlinked config file must keep the name the user gave it, not relocate to the symlink's target (see `atomic_write_resolved`'s dotfiles-repo pattern)
- `resolve_relative_path(path, base)` — resolve relative to base with traversal validation
- `validate_path_within(path, root)` — canonicalize and verify path within root
- `validate_no_traversal(path)` — reject a user-written path reference that contains `..` **or** that names nothing of its own (`.`, `./`, so it would resolve to the directory it is joined onto). Use for paths cfgd reads from or writes to; a leading `./` stays legal
- `validate_plain_name(raw)` — stricter, and judged on the raw string because `Path::components()` normalizes `.` away: every `/`-or-`\`-separated segment must be an ordinary name (`daily/2026` ok; `.`, `daily/.`, `./daily`, `daily/`, `daily//x` rejected), and the value must not be rooted (`/daily`, `C:/daily`, `C:daily`, `\\server\share` — `Path::join` throws the base away for a rooted RHS) or contain `:` anywhere (Windows drive-relative + NTFS data streams). Windows shapes are rejected on every host so a name is valid everywhere or nowhere. Use for any string that NAMES something cfgd creates under a root it may later delete or mount wholesale — source names, CSI cache module/version, backup snapshot names
- `atomic_write(target, content)` — atomic write via temp+rename; returns SHA256 hash; use instead of `fs::write()` in ALL production code. A symlink at `target` is REPLACED by the new regular file, which is what a deployed module file wants (following the link would write back over the module's own source). Under root it preserves the destination's uid/gid (or the parent directory's, when creating), so `sudo cfgd apply` cannot leave a root-owned file in a user's home
- `atomic_write_str(target, content)` — string variant
- `atomic_write_merged(target, content)` — the `strategy: Patch` write: resolves a symlinked `target` to the real file first, then `atomic_write_str`. Use for any write-back over a file cfgd does not own, so the target keeps its mode (rename-replace, never delete-then-create) and its link identity
- `atomic_write_resolved(target, content)` / `atomic_write_resolved_str(...)` — the FOLLOW-the-symlink variants: resolve `target` through an existing, canonicalizable symlink and write the destination, leaving the link intact. For rewrites of a user-owned file cfgd did not author (rc files, `~/.cfgd.env`), where a stow/chezmoi-style link into a dotfile repo must survive. A dangling link is written at the link path itself, so a planted broken link cannot redirect the write
- `ensure_parent_dir(target)` — create the parent directory of a file path (and ancestors) if missing; use instead of the inline `if let Some(parent) = path.parent() { create_dir_all(parent)? }` idiom before writing a file. For creating a named directory itself, call `create_dir_all` directly
- Scaffold writes in the `cfgd` binary crate go through `write_scaffold(kind, path, body)` in `crates/cfgd/src/cli/helpers.rs` — pairs `with_schema_modeline` (pinned to the binary crate's `CARGO_PKG_VERSION` by construction) with `atomic_write_str`. Never stamp a modeline with cfgd-core's version; rewrite paths of user-owned files (e.g. `save_module_document`) stay modeline-free and must NOT use it
- Rewrites of user-owned YAML in the `cfgd` binary crate go through `rewrite_user_yaml(path, &value)` in `crates/cfgd/src/cli/helpers.rs` — serializes via serde_yaml and re-prepends the file's existing leading comment block (banner + modeline) using `cfgd_core::config::with_leading_comments(original, serialized)` (capture primitive: `leading_comment_block(original)` in `cfgd-core/src/config/comments.rs`). Preserve-only, never inject; mid-document comments are not recoverable. Use instead of raw `serde_yaml::to_string` + `atomic_write_str` on any user-owned manifest (`mutate_config_yaml` composes `with_leading_comments` inline because it also validates)
- `copy_dir_recursive(src, dst)` — recursively copy a directory tree. Skips symlinks on the READ side and creates the destination itself, so it is only correct when cfgd owns the destination. Writing into live user data (a restore overlay) needs a walker that stats each destination entry unfollowed — see `backup/restore.rs::overlay_dir`
- `carry_dir_mode(src, dst)` — best-effort copy of a directory's mode; no-op on Windows. Call it AFTER populating `dst`, or a restrictive source mode blocks the very writes it is being applied around
- `create_symlink(source, target)` — cross-platform; Windows errors with Developer Mode guidance
- `is_same_inode(a, b) -> bool` — check same file (inode+dev on Unix, file index+volume on Windows)
- `file_identity(path) -> Option<FileIdentity>` — the same identity as ONE value, captured now and compared later, for a holder that opened a file and must notice the path being re-pointed at a different one. `is_same_inode` is the two-paths-at-one-moment view over it and is derived from it, so the two can never disagree about what "the same file" means. `None` when the path names nothing or cannot be stat'd, which a caller reads as "cannot say" rather than as "different" — the daemon's held SQLite connection re-derives it on every lend and reopens on a mismatch (cfgd itself renames the state database during a legacy-state-dir migration, and a connection left on the orphaned inode writes into nothing, silently, forever). Same pattern as `acquire_lock_at`'s post-acquire re-check: after taking the thing, verify the path still names it
- `try_file_identity(path) -> io::Result<FileIdentity>` — the same probe REPORTING why it failed, and what `file_identity` is the `.ok()` view over. Reach for it wherever "this is not the file I opened" and "I could not look" must lead to different actions: only `ErrorKind::NotFound` means the path stopped naming what it used to, while every other error (a parent directory that lost `+x`, a sharing violation from a third party on Windows, where the probe is a `File::open` rather than a stat) means the question went unanswered and a holder should keep what it has. Collapsing the two is how a transient error closes a working connection
- `file_permissions_mode(metadata) -> Option<u32>` — Unix mode bits; `None` on Windows
- `set_file_permissions(path, mode)` — set Unix mode; no-op on Windows
- `is_executable(path, metadata) -> bool` — Unix exec bit; Windows checks `.exe/.cmd/.bat/.ps1/.com`
- `capture_file_state(path)` — capture content/permissions/symlink state; returns `Option<FileState>`
- `capture_file_resolved_state(path)` — like above but follows symlinks
- `FileState` — struct (content, hash, permissions, symlink info, oversized flag)

## Process / commands

**The 30-second convention.** Four process-scoped memos now sit at a 30s ceiling — `command_path`'s, `ENUMERATION_MEMO_TTL`, `AVAILABLE_VERSION_MEMO_TTL` and `REPO_REFRESH_TTL` — and a fifth should pick the same number rather than invent one. The rule the number encodes: a memo whose FIRST bound is `command_resolution_generation()` (everything cfgd itself does) needs a second bound for the changes cfgd cannot see — a package a human installed by hand, a tag someone pushed — and 30s is short enough that a long-lived daemon notices within one tick and long enough that a single CLI invocation never pays the question twice. Each keeps its OWN named constant on purpose: they answer four different questions, and one shared constant would make tuning any of them move the other three. Every one is pinnable from tests by its own RAII guard, and every memo also carries a 1024-entry cap so its size is independent of how long the process runs.

**Which exclusion a TTL guard needs is decided by what its tests assert on**, and the three memos answer it three different ways on purpose — copying a sibling's answer is how a test ends up excluding the wrong thing. Ask what a concurrent pin would change in the assertion:

| The test asserts on | What a concurrent pin can do to it | The exclusion it needs |
|---|---|---|
| An ANSWER the memo returns (`command_path` resolves this binary) | Nothing — a longer TTL only lets entries live longer, a zero TTL only recomputes them, and neither changes the answer | None. `CommandPathMemoTtlGuard` carries no serialization |
| A COUNT of the work the memo saved (one version query, one enumeration) | Everything — another test's zero pin makes the memoized answer recompute, which is exactly the number being measured | A named `serial_test` group (`available_version_memo`, `enumeration_memo`), declared at every call site |
| WHETHER SOMETHING HAPPENED at all (a transfer was attempted / was spared) | Everything, and the surface is not a counter it can share a group with | The lock inside the guard (`GitRefreshWindowGuard`), taken by construction so no call site can forget it |

The lock is the strongest of the three and still the narrowest: it excludes other PINS, never an unpinned concurrent reader of the same process-global setting. Any test whose claim turns on the pinned value must therefore pin — in whichever direction it needs — rather than assume the default is live.

- `command_available(cmd)` — check if a CLI command exists on PATH
- `command_path(cmd)` — resolve a command to its full executable path (PATHEXT-aware on Windows); `command_available` is the `is_some()` view over it. Searches `$PATH` first, then the directories registered by `register_bootstrapped_path_dirs`. MEMOIZED per command name, and a miss is memoized too because a miss is the expensive answer — it stats every directory on `PATH` before it can say no, and the callers are loops (the apply dispatcher asks per dispatch iteration per slot, the module planner asks inside a sort key, the secret planner asks per declared reference). Each entry carries the exact `PATH` value and the `command_resolution_generation()` it was computed under, plus a 30s ceiling on its own age (the generation covers every install cfgd performs; the ceiling is what lets a weeks-long daemon notice one a human performed by hand). Anything that no longer matches is walked again. The key travels with the ENTRY rather than sitting on the map, so a lookup under a different `PATH` cannot evict an entry it merely disagrees with — the suite changes `PATH` on one thread while another asks about it. `PATHEXT` is not part of the key because it is not part of resolution: the Windows extension list is a fixed literal, not an environment read
- `command_resolution_generation()` / `invalidate_command_resolution()` — the ONE counter behind BOTH memos (`command_path`'s and `ProviderRegistry`'s availability sweep), so one bump makes both re-ask and a mid-apply bootstrap flips "unavailable" to "available" on the very next question. Bumped by `register_bootstrapped_path_dirs` and `restore_bootstrapped_path_dirs`, and CALLED EXPLICITLY from every path that puts a binary on the machine — or TAKES ONE OFF IT — without registering or unregistering a directory: `PackageExec::install_recording_created` (an `apt install curl` lands in a directory already on `PATH`), the `PackageAction::Uninstall` arm (the mirror: a removal is the same invisible event, and a memo that kept answering `Some(path)` for a binary the run deleted would have the next tick plan against a tool that is gone), the `ManagerAction::Provision` arm (before the outcome propagates — a cascade that failed at its last step may still have installed the manager, and the availability check right after it must not read a memo predating the install), `reconciler::scripts::execute_script_with_tty` (a `preApply` hook installing a toolchain is the one effect cfgd cannot predict), and `packages::prune_orphaned_packages` (its persisted uninstall script takes binaries off the machine exactly as a manager's own uninstall does; the bump is unconditional and BEFORE the outcome is matched, because a partial failure has already removed whatever it removed). Add a call to any new path of that shape; the cost is one atomic increment and the cost of missing one is a manager that stays missing for the rest of the run
- `ProviderRegistry::package_managers()` / `system_configurators()` + `add_package_manager` / `extend_package_managers` / `set_package_managers` / `add_system_configurator` / `extend_system_configurators` in `cfgd-core/src/providers/mod.rs` — the read and write halves of the two provider vectors, which are PRIVATE. Registration is the second thing (after an install) that retires an availability sweep, and every mutator clears the memo for its own vector, so a registry cannot be left holding a sweep that describes providers it no longer has — the CLI builds a registry in stages and adds custom managers after a plan has already asked what is available. Never widen the fields back to `pub`: a caller that could push, swap, or truncate directly would reintroduce exactly the shape the memo cannot detect, and no key on the memo side can close it (an in-place `vec[i] = …` keeps the length identical)
- `PackageContext::installed_for(manager) -> Arc<InstalledPackages>` in `cfgd-core/src/providers/mod.rs` (memo in `providers/installed.rs`) — the ONE question "what does this manager report installed", and what every diff-against-installed surface reads from: `reconciler::verify`, `reconciler::stale_tracked_packages`, `packages::plan_packages`, `compliance::collect_package_checks` + `collect_watched_package_manager_checks`, `cli::diff::package_missing_drift` (reached per package from both `cfgd diff` and `cfgd status`), `cli::doctor::package_is_installed`, and `generate::scan::scan_installed_packages` (one generate session holds ONE context across up to 100 tool turns). Never call `installed_packages[_with_versions]` directly from a caller that holds a context — a per-package call re-ran the manager's listing once per declared package, which is the multi-second `status` scan. One call to `installed_packages_with_versions` per manager per generation backs BOTH views: `identities()`/`contains()` (every listed name folded through `listed_identity`, the identity space the planner diffs in) and `listed()` (names + versions as listed). Asking both trait methods asks the machine the same question twice — `listed_identity` exists to map one into the other — and the versioned call is the one that survives because the version half cannot be recovered from a bare name set. Keyed by REGISTERED manager name, never `manager_family`: `brew` and `brew-cask` list different populations. The whole get-or-enumerate protocol lives in `InstalledEnumerations::get_or_enumerate` and `installed_for` is a wrapper over it, because `PackageContext` borrows its printer and state store and so is neither `Send` nor `Sync` — the enumerations map is both, and is the only half a concurrency test can put under two threads. Locking is two-level: the map lock is held only long enough to hand out a per-manager slot, never across an enumeration, so an `apt` listing in flight cannot hold up a question about `npm`; the slot lock IS held across its own manager's listing, which is the same one-operation-per-manager rule the apply lanes run under. The memo is per-CONTEXT by default — a context is moved, never cloned, and each lane worker mints its own via `PackageExec::cx`. The one path that SHARES one is `PackageContext::with_shared_enumerations(printer, state, enumerations)`, for a host that outlives the context it builds: the MCP server holds an `InstalledEnumerations` for its whole life and lends it to the context it mints per tool call, which otherwise re-enumerated every manager on every call. Lending is what the per-slot locking is for. Invalidation is DOUBLE-bounded, and the second bound is what makes lending safe. `command_resolution_generation()` covers every change cfgd itself performs — every path that installs, uninstalls, provisions or runs a lifecycle script already bumps it — and a 30s age ceiling (`ENUMERATION_MEMO_TTL`, modelled on `command_path`'s) covers the ones it does not: a package a human installed by hand, and the MCP server's session-long lend, whose host never installs anything and so never moves the generation. Neither bound alone is sufficient: a generation-only memo lent across an hour-long MCP session would answer from its first minute forever. Pin the ceiling in a test with `test_helpers::EnumerationMemoTtlGuard` and pair it with `#[serial_test::serial(enumeration_memo)]`, because the pin is process-global and every enumeration test asserts on a COUNT. An enumeration ERROR is not memoized. A `PackageManager` must never call it from inside its own enumeration (its slot lock is held). A command that reads installed state in two places builds ONE context and threads it (`cfgd verify`, `cfgd apply`), rather than building a second one that re-asks every manager
- `ProviderRegistry::manager_map()` in `cfgd-core/src/providers/mod.rs` — the ONE construction of the `name → &dyn PackageManager` map every module-resolution entry point takes (`resolve_package`, `resolve_module_packages`, `resolve_modules`, `fill_available_versions`). Thirteen call sites across the CLI and two inside the daemon each built the same collect by hand; the CLI's `cli::helpers::managers_map` was one of them and is gone. Keyed by the REGISTERED name, never `manager_family` — a copy that folded the family would answer a `brew-cask` question with `brew`'s managers
- `PackageManagerExt::available_version_memoized(package)` in `cfgd-core/src/providers/mod.rs` (memo in `providers/available.rs`) — the ONE question "what does this manager currently OFFER for this package", and the sibling of `PackageContext::installed_for`'s "what does it HAVE". Blanket-implemented over every `PackageManager`, so `dyn` call sites reach it. Never call the trait's `available_version` directly from a resolution or display path: the query is a subprocess and a network round-trip for `npm`/`cargo`/`pipx`, and the same package is asked about once per module that declares it, once per candidate manager, and again by any display fill. Keyed by `(REGISTERED manager name, package)` — `brew` and `brew-cask` offer different packages under one binary. Unlike the enumeration memo this one is PROCESS-scoped, because its callers (a free function reached with nothing but a manager map, plus two CLI introspection surfaces) share no context object; what makes that safe is the same double bound — `command_resolution_generation()` covers every install/uninstall/provision/lifecycle-script cfgd performs, and a 30s ceiling covers a package a human installed by hand. The lock is NOT held across the query, so two threads racing for one key may both ask; a per-key slot lock buys one saved subprocess in a race the single-threaded callers do not have. An error is never recorded. Pin the ceiling in a test with `test_helpers::AvailableVersionMemoTtlGuard` and pair it with `#[serial_test::serial(available_version_memo)]`. Because the key is the manager NAME, two test fixtures claiming that one manager offers two different versions of one package are claiming two different machines, and whichever runs second reads the other's answer — make fixtures agree. In PRODUCTION the name is a sufficient key and the question is closed: `manager_map` is keyed by name so exactly one manager ever answers, two registries in one process are built from the same binary and the same config (the daemon rebuilds one per tick; `diff`/`doctor` build two), and the MCP server is handed a single `config_path` at startup, so one process never serves two configs. The one reachable staleness is a user redefining a CUSTOM manager's version command while a daemon is live — bounded at 30s or the next generation bump, the same shape every sibling memo carries
- `SecretCache` in `cfgd-core/src/providers/secret_cache.rs`, re-exported as `cfgd_core::providers::SecretCache` — the ONE resolution of a secret per `(backend, reference)` per RUN, and what both surfaces that interpolate secrets read from: the reconciler's env/file secret actions (`reconciler/secrets.rs`, one cache per `Reconciler`) and the file manager's `${secret:` rendering (`files/apply.rs`, one cache per `apply` CALL). `resolve_with(backend, reference, resolve)` hands back an `Arc<SecretString>`, so the same reference named by a `Resolve` action, a `ResolveEnv` action and five templates spawns `op`/`bw`/`vault`/`sops` ONCE instead of once per occurrence. Errors are never recorded — a backend that failed is asked again. Unlike every other memo in this catalog it is deliberately NOT process-scoped and takes no TTL: it holds PLAINTEXT, so its lifetime is the unit of work and nothing longer. That is also why the file manager's lives on the `apply` call rather than on the manager — the daemon holds one registry (and so one file manager) across ticks, and a cache on the manager would keep a rotated secret's old value for the daemon's life. It is never persisted, never logged, and its `Debug` prints the entry COUNT and nothing else; values are `secrecy::SecretString`, which zeroizes on drop. A reference used by both surfaces costs two resolutions on purpose: one shared cache would mean plaintext outliving the narrower of the two scopes
- `modules::fill_available_versions(packages, managers)` / `fill_module_available_versions(modules, managers)` in `cfgd-core/src/modules/resolve.rs` — the ONE place a resolved package is PRICED for display. `resolve_package` no longer asks unless a `minVersion` constraint makes it look anyway, so `ResolvedPackage.version` is `None` until one of these runs; call them from a surface that RENDERS a version and from no other. The rule is not a list to memorize: **every** caller of `Reconciler::plan` fills, because that planner's `InstallPackages` description renders `brew install neovim (0.10.2)` and is also the persisted action description and the module's recorded `packages_hash` — a plan built over unfilled modules renders AND STORES a different string than the same modules applied from anywhere else, so `cfgd module show`'s packages-hash line changes depending on which command last touched the module. That is six sites: `cmd_apply`, `cmd_plan`, the daemon's reconcile tick, both `cfgd init` apply paths (`cli/init/cmd_init.rs`) and `cfgd module create --apply` (`cli/module/crud.rs`) — the last three were missed on the first pass, and no snapshot binary covers them. Two more surfaces print a version per declared package without planning (`cfgd doctor`, `cfgd module show`), for eight in total. The daemon's COMPLIANCE tick shares `resolve_daemon_modules` and deliberately does not fill — nothing it stores renders a version. The gating reproduces what resolution used to do exactly, so those eight surfaces render byte-identically: a package already carrying a version is left alone, a `script` package has no manager to ask, and an unavailable manager is not asked (a bootstrappable one resolved optimistically with no version before this existed and still does). Every read command — `status`, `diff`, `verify`, `compliance`, `checkin`, `decide` — paid one subprocess per declared package per invocation for a string it never printed
- `register_bootstrapped_path_dirs(dirs)` — make the PATH directories cfgd created for a package manager THIS RUN visible to every later `command_path` / `command_available` call in the process. Called from `PackageExec::record_path_dirs`, the ONE registration point for both a bootstrap's `path_dirs` and the prefix an `install()` created (`created_path_dirs`); without it the action after a bootstrap cannot resolve the binary that bootstrap just installed (brew lands `pipx`, the next action is `pipx install …`). Deliberately not `std::env::set_var("PATH", …)`, which is unsound once any thread is live
- `bootstrapped_path_dirs()` — snapshot of the above; the process-scope counterpart to the state-backed `reconciler::all_recorded_path_dirs`, which is what lifecycle scripts get
- `path_with_dirs_prepended(current, dirs)` — the ONE composition of a `PATH` whose leading entries are `dirs`. `None` when the value would not change (`dirs` empty, or every one already on `current`) and `None` when `join_paths` refuses a directory containing the platform separator, so a caller leaves the environment alone rather than re-setting a variable to itself or splitting one bogus entry into two. Two callers hand the same bootstrapped directories to two halves of one run and must agree: a lifecycle script's environment (`reconciler::scripts::prepend_bootstrapped_path_dirs`) and a package manager's child process (`packages::shared::hand_child_bootstrapped_path`, called from every spawn wrapper — `pkg_run`, `run_pkg_cmd_prefixed` and `run_pkg_query` — because a full-path `npm` still spawns `node` and `git`, and a QUERY (`npm config get prefix`, `pipx list`) exits 127 exactly as an install would). Prepends rather than appends, matching `generate_env_file_content`, because the manager cfgd installed is the copy it meant. An EMPTY `current` contributes no entries at all: `std::env::split_paths("")` yields one empty entry, which POSIX reads as the current directory, and composing that back would put `.` on every child's PATH
- `process_path_with_dirs_prepended(dirs)` — the same composition over THIS PROCESS's `PATH`, and what every consumer outside cfgd-core calls. It exists so the read is bracketed by `path_env_read_guard()` the way every other production `PATH` reader is: the guard is gated on the `test-helpers` feature, which a `cfgd`-crate call site cannot name, so a caller reading `std::env::var("PATH")` by hand re-opens the window ahead of a guarded spawn that the lock exists to close
- `restore_bootstrapped_path_dirs(dirs)` — overwrite the registry; gated behind `cfg(any(test, feature = "test-helpers"))` because production never rewinds it. Reach for it through `test_helpers::BootstrappedPathDirsGuard`, never directly
- `command_output_with_timeout(cmd, timeout)` — run `Command` with timeout, kill on exceed; use for any external command that could hang. It OWNS the stdio configuration (stdout/stderr piped, stdin null) and drains the pipes on reader threads, so callers must not set stdio themselves — a caller that leaves it alone still gets captured output, and one that pipes by hand is redundant, not required
- `terminate_process(pid)` — SIGTERM (Unix) / TerminateProcess (Windows)
- `exit_status_reason(status)` — the ONE rendering of why a child process ended, for any failure message naming an `ExitStatus`: `exit code {n}` when it returned one, `killed by signal {n} ({NAME})` when a signal ended it (SIGHUP/INT/ABRT/KILL/SEGV/PIPE/TERM are named; anything else keeps the number), and `terminated without an exit code` on a host that reports neither. Never write `status.code().unwrap_or(-1)`: cfgd kills a child itself on abort and on a `command_output_with_timeout` overrun, so the most common signalled exit is one cfgd caused, and `-1` names an exit code no process ever returned while hiding the signal that would explain it. Both failure surfaces read from here — `packages::shared::command_failure_reason` (a package manager's non-zero exit) and `reconciler::scripts` (both script-failure sites)
- `stdout_lossy_trimmed(output)` — trimmed lossy-UTF8 stdout from `Command` output
- `stderr_lossy_trimmed(output)` — trimmed lossy-UTF8 stderr
- `is_root()` — elevated privileges check: euid==0 (Unix) / IsUserAnAdmin() (Windows)
- `hostname_string()` — system hostname as `String`; `"unknown"` on failure
- `tracing_env_filter(default)` — `EnvFilter::try_from_default_env().unwrap_or_else(EnvFilter::new(default))`
- `require_tool(name, install_hint)` — uniform "X not found" error message, used by all `command_available`-gated CLI flows
- `systemctl_cmd()` / `systemctl_available()` / `SYSTEMCTL_BIN_ENV` — the ONE `systemctl` factory, its availability predicate, and the `CFGD_SYSTEMCTL_BIN` seam name they share. Every `systemctl` invocation in the workspace is built here and bounded by `command_output_with_timeout`: five call sites across three crates spawn it (`system/systemd_unit.rs`, `system/node/{kubelet,containerd}.rs`, `generate/scan`, `daemon/service/systemd.rs`, `env_session.rs`), so one spelling is what lets a test redirect all of them at once, and an unbounded call on a host carrying the binary without a running manager — a container, WSL, a chroot — blocks for the ~90s D-Bus connect timeout PER UNIT before failing. Never write `Command::new("systemctl")` or `command_available("systemctl")`: the first is unshimmable and unbounded, the second answers from `PATH` while the spawn answers from the seam, so a shimmed test reads "unavailable" and skips the branch it installed the shim for
- `reg_cmd()` / `REG_BIN_ENV` — the ONE `reg` factory and the `CFGD_REG_BIN` seam name, the registry's counterpart to `systemctl_cmd`. Two places read and write the Windows registry — the user-session environment refresh (`util/env_session.rs`) and the `windowsRegistry` configurator (`system/windows_registry.rs`) — and a test can only redirect both when they agree on one spelling; the registry is not a path, so redirecting the BINARY is the only sandbox a test has. It is also what lets the registry configurator's spawn count be proven off Windows: `RegKeySnapshot::read` stands down on a non-Windows host with no seam set, and runs when one is
- The keyed system configurators each name their own seam beside their `tool_cmd` factory — `CFGD_GSETTINGS_BIN`, `CFGD_XFCONF_QUERY_BIN`, `CFGD_KREADCONFIG_BIN` / `CFGD_KWRITECONFIG_BIN`, `CFGD_DEFAULTS_BIN` — and `windowsRegistry` reaches the shared `reg_cmd()` seam (`CFGD_REG_BIN`, in `util/process.rs` beside `util/env_session.rs`'s use, per the bullet above) — but they do NOT all gate availability the same way, and the difference is what a test has to plan around. `gsettings` and `xfconf` pair their seam with `command_available_with_seam`, so `is_available` and the spawn answer from the same place. `kdeConfig` does the same and then answers the v6-or-v5 generation question from the seam too (`seam_is_set`), because the fallback probe is a question about the HOST and a set seam means the host is not what runs. `macosDefaults` and `windowsRegistry` are PLATFORM-gated instead (`cfg!(target_os = "macos")` / `cfg!(windows)`), so their `is_available` is false off-platform however the seam is set; what the seam buys there is the SPAWN, which is what lets their spawn counts be proven on Linux — `windowsRegistry` carries the gate on the read itself (`RegKeySnapshot::read` returns an empty snapshot on a non-Windows host with no `CFGD_REG_BIN` set, and spawns when one is), while `macosDefaults` spawns unconditionally and simply finds no `defaults` on a foreign host, so a shim is what makes it answer at all. A test drives all of them through `test_helpers::ToolShim`, and asserts on `argv_lines_naming(subject)` rather than the whole log, because an env-var seam is process-global and carries no exclusive guard

## Git

- `git_cmd_safe(url, ssh_policy)` — build a `Command` for git with `GIT_TERMINAL_PROMPT=0` and configurable `StrictHostKeyChecking`; required for any operation that may touch a remote (clone, fetch, ls-remote)
- `git_cmd_local()` — build a `Command` for git suitable for LOCAL-only operations (`config` get/set, `tag -v`, `add`, `commit`, `rev-parse`, `log`). Sets `GIT_TERMINAL_PROMPT=0` (still desirable — prevents prompt-driven hang if git unexpectedly tries to authenticate) but skips `GIT_SSH_COMMAND` since no network is involved. Use instead of `std::process::Command::new("git")` for every local git invocation
- `try_git_cmd(url, args, label, ssh_policy)` — run via `git_cmd_safe`, return `true` on success; use before every git2 network operation as CLI-first fallback to prevent SSH hangs
- `resolve_repo_reference(value) -> Cow<'_, str>` in `cfgd-core/src/util/git.rs` — the ONE resolution of a user-written repository reference, and what EVERY user-facing entry point calls: `cfgd init --from` (and `apply --from` / `plan --from` through the shared `cli::init::source::resolve_from`), `cmd_source_add`, `cmd_source_replace`, `cmd_module_registry_add`. An existing local path wins; everything else routes through `expand_github_shorthand`. `acme/config` is simultaneously a valid shorthand and a valid relative path and only the filesystem can say which the user meant, so a surface that skipped this step answered a local directory with a network fetch of a same-named GitHub repository — which is what three of the four did while only `init --from` checked. Presence is judged with `symlink_metadata`, not `Path::exists`: a dangling symlink is still an entry the user created under that name. Resolution is idempotent and the pass-through arm allocates nothing. Being a local path is NOT the same question as being a legal source ORIGIN — `SourceManager::load_source` refuses every local origin (see `is_remote_origin_url`), so `source add ./acme/config` is reported as the local path it is instead of being silently redirected
- `expand_github_shorthand(value) -> Cow<'_, str>` — the ONE expansion of a GitHub `owner/repo` shorthand into `https://github.com/owner/repo.git`, and the only place the rule for what counts as a shorthand lives. It answers from the STRING alone; reach for `resolve_repo_reference` in any command path, and for this only where no filesystem question exists. Expansion is idempotent, so a caller may resolve an already-resolved value; the pass-through arm borrows and allocates nothing. Pass-through classes: explicit schemes (`https://`, `http://`, `ssh://`, `git://`, `file://`), SCP-style remotes (`git@host:owner/repo.git`), dot-carrying hosts, path-shaped values (`/srv/x`, `./x`, `~/x`, `C:\x`), a repo stem of nothing but dots (`acme/..` is a path, never a repository), and anything that is not exactly two `/`-separated segments. The host test is a dot anywhere in the FIRST segment: a GitHub login admits only ASCII alphanumerics and hyphens, so a dotted first segment is a hostname and never an owner — that is what keeps `gitlab.example.com/acme/config` pointed at its own server instead of being silently redirected to github.com. A repo name MAY carry dots (`acme/acme.github.io`), so the test never widens past the first segment. A DOTLESS host (`localhost/config`, `gitserver/config`) is indistinguishable from an owner by grammar alone and does expand; the docs say to name such a host with a scheme rather than implying a guarantee the dot test cannot give
- `detect_default_branch(repo_dir)` — best-effort detection of `origin/HEAD` then local `HEAD`; returns `Option<String>`
- `detect_git_remote()` — `origin` remote URL of the repo containing the CWD; `None` outside a repo / no origin. Stamps artifact provenance; use for any push/pack command instead of re-deriving
- `detect_git_head()` — `HEAD` commit SHA of the repo containing the CWD; `None` outside a repo / no commits. Stamps artifact provenance
- `git_ssh_credentials(url, username, allowed)` — git2 credential callback (SSH agent + HTTPS helper)
- `fetch_git_source(git_src, cache_base, module_name, printer)` in `crates/cfgd-core/src/modules/git.rs` — the ONE materialization of a module's git file source into the cache, and the only thing in the workspace that decides whether a transfer is needed. Two short-circuits sit in front of the fetch and neither may be re-derived at a call site. (1) A ref that is a full 40-character ASCII-hex object id the cached checkout already holds is NOT fetched: the commit is immutable, so a transfer could only re-deliver what is already there. The predicate is `git2::Repository::find_commit` on the parsed Oid — the library spelling of `git cat-file -e <sha>^{commit}` — and it stands down when a `refs/tags/<name>` or `refs/remotes/origin/<name>` of the same spelling exists, because `checkout_ref` prefers those and a moving ref that merely LOOKS like a SHA must still be refreshed. A tag or branch pin always fetches: both can move. (2) A per-RUN refresh window keyed by repository URL, so one repository is transferred once however many files, modules or locked entries name it — both fetch paths use the remote's configured refspecs, so one `git fetch origin` brings every ref anyone will ask for. Three callers share repositories in practice (`resolve_module_files`, `load_locked_modules`, the registry scan) and each used to pay its own network round-trip. The window is only HALF the skip condition and never widens to the whole of it: the cache must also RESOLVE the ref this caller asked for (`cache_resolves_ref`, which mirrors `checkout_ref`'s tag → remote-branch → bare-revision order through the shared `named_ref_candidates`). `cfgd module upgrade` is the shape that proves why — one process clones at the version being upgraded FROM and then asks for one published after that clone, and a window keyed on the repository alone answers the second ask with the first transfer, failing the upgrade with `cannot find ref`. Pin the window in a test with `test_helpers::GitRefreshWindowGuard`. An UNPINNED source (no tag, no `?ref=`) is advanced onto its remote-tracking branch after the transfer, because a fetch updates `refs/remotes/origin/*` without touching the working tree and stopping there froze the deployed files at the original clone's commit forever. The branch is read from `refs/remotes/origin/HEAD`, and when a clone left none it is recovered from the checked-out branch and WRITTEN BACK as that symbolic ref — the advance detaches HEAD, whose shorthand names no branch, so an unrecorded answer would be good for exactly one advance
- `is_git_source(value)` in `crates/cfgd-core/src/modules/git.rs`, reached as `cfgd_core::modules::is_git_source` — the ONE git-URL predicate. Pure and scheme-based: `https://`, `http://`, `ssh://`, `git://`, SCP-style `git@host:…`, plus `file://` behind `CFGD_ALLOW_LOCAL_SOURCES`. Four callers judge a value here and must agree — `parse_git_source`'s guard, the module file-source classification in `modules/resolve.rs`, `is_registry_ref`'s negation, and `cli::init::source::is_clonable_source` — so a URL accepted at one is accepted at all. Deliberately does NOT probe the filesystem or accept a bare `.git` suffix: a module declaring `source: files/nvim` must stay a local path even when the config repo around it is a git work tree. `cfgd init --from` is the one caller that may also be handed a repository on the same machine, and it layers three extra arms in `is_clonable_source` rather than widening this predicate for everyone: a `.git` suffix, a `<value>/.git` filesystem probe, and `file://` — answered CLI-side precisely BECAUSE this predicate gates `file://` behind the process-global `CFGD_ALLOW_LOCAL_SOURCES`. That gate protects composed SOURCES from naming the local filesystem; `--from` is the user naming their own config repo on the command line, and classifying it by an env var no `--from` caller sets would make the answer depend on whatever else the process has done. A second copy of this predicate previously lived in the CLI and had drifted into accepting shapes the core rejected

## Hashing / versions

- `sha256_hex(data)` — SHA256 of `&[u8]` as lowercase hex; use instead of inline `Sha256::digest` patterns
- `sha256_digest(data)` — OCI-style `sha256:<hex>` digest string
- `strip_sha256_prefix(s)` — strip `sha256:` prefix; idempotent if no prefix
- `Sha256Stream` in `cfgd-core/src/util/hashing.rs`, re-exported as `cfgd_core::Sha256Stream` — the incremental form of the two above, for a digest over MANY inputs where at least one is a file: `new()`, `update(&[u8])` for an in-memory part, `absorb_file(&Path)` for a file read in 64 KiB chunks, then `finish_hex()` / `finish_digest()` (the `sha256:`-prefixed form). Reach for it instead of `fs::read`-ing each file into a `Vec` and concatenating — `hash_module_contents` held every byte of a module tree in memory twice (once per file, once in the joined buffer) to produce a digest of a stream it never needed to keep. It is byte-for-byte the same digest as feeding the same parts to `sha256_hex`/`sha256_digest`, which is what lets an existing lockfile keep verifying; the seam order (each part, in the caller's order) IS the digest, so never reorder or re-delimit a caller's parts. `digest 0.11` implements no `io::Write`, so the chunk loop is hand-rolled here rather than through `io::copy` — do not re-derive it at a call site

## Locks / reconcile

- `acquire_apply_lock(state_dir)` — exclusive apply lock; `flock` on Unix, `LockFileEx` on Windows; returns `ApplyLockGuard` (RAII release)
- `acquire_source_lock(cache_dir, on_wait)` — the source-cache mutex at `<cache_dir>/cache.lock` (`SOURCE_CACHE_LOCK_FILENAME`; deliberately NOT named `sources.lock`, which is the SHA lockfile beside the user's config — `sources/lockfile.rs`), built on the same `acquire_lock_at` primitive as the apply and backup locks. Held by `SourceManager::load_source` across the origin check, the discard of a mismatched checkout, and the clone/fetch that replaces it, because the cache is keyed by the source NAME alone and two cfgd processes naming one source can otherwise interleave a fetch against a re-pointed `origin` or a clone against a tree being removed. The one lock that BLOCKS rather than refusing (`LockWait::Block`): the section is one clone, both contenders want the same end state, and refusing would fail a run over an overlap that resolves itself. `on_wait` fires at most once, only under contention, so the caller can say what it is waiting for instead of appearing to hang. Deliberately not the apply lock, so a read path is never refused because an apply holds it. `validate_source_name` reserves the filename, so no checkout can occupy the lock's path. **Nothing in cfgd ever deletes a lock file**, and a failed first-ever load deliberately leaves an empty cache root and a zero-byte `cache.lock` standing rather than taking them back: deleting a lock file strands whoever is already blocked on it, and no amount of ordering fixes that, because the contender is inside a syscall on an inode the unlink orphans. Tidying that residue is not worth a split section — the next load reuses both files. What guards the case cfgd does NOT control (a user wiping the cache directory mid-run) is in `acquire_lock_at`: after the lock is granted it re-checks that the file it locked is still the one the path names, re-opens when it is not (re-creating the directory first, or the contender fails `ENOENT` for having waited; a short bounded backoff between re-opens gives a Windows delete-pending window time to clear), and once the re-open budget is spent reports `StateError::LockFileUnstable` naming the lock path — never a guard over a file the path no longer names, and never the held-lock error, because nobody is known to hold anything and the source path must not read exhaustion as contention. `record_pid` and the guard's drop-time clear both address the HELD HANDLE, never the path, so neither can write into a file this process does not hold. Never route either through the path, and never drop the re-check. Every `on_wait` in the workspace announces through `printer.alert(...)`, never `status_simple`: `cfgd sync` hands `load_source` a printer derived at `Verbosity::Quiet`, which drops every role but `Fail`, so an ordinary status line leaves the command animating a spinner for an unbounded wait and saying nothing
- `sources::discard_cached_checkout(cache_dir, name, printer)` in `crates/cfgd-core/src/sources/mod.rs` — the ONE deletion of a source's cached checkout, holding `acquire_source_lock` across the removal. Both deleting surfaces reach it: `SourceManager::remove_source` and `cli::source::remove` (which cannot use `remove_source`, because it never populates the in-memory `sources` map that method's `NotFound` is judged against). Never write a bare `remove_dir_all` over `<cache_dir>/<name>` at either — unserialized, `cfgd source remove` deletes the tree a concurrent `cfgd sync` is cloning into, the same interleaving the lock closes on the load side. An already-absent checkout is `Ok`: the caller asked for its absence and another process delivered it
- `resolve_effective_reconcile(module, profile_chain, config)` — resolve per-module reconcile settings from patches
- `EffectiveReconcile` — resolved (interval, auto_apply, drift_policy) with no Options

## Config inputs (what a derivation READ)

- `record_config_input(path)` in `cfgd-core/src/util/config_inputs.rs`, re-exported as `cfgd_core::record_config_input` — the ONE report that a file (or a directory listing) was consulted while turning YAML on disk into cfgd's typed config. Called from the READ sites themselves — `config::load_config` / `load_profile` / `find_profile_path`, `sources::read_manifest` + the cached-source directory, both lockfile readers, and the module loader's document reads and `modules/` listing — so a caller that wants to know whether a derivation is still current never has to GUESS the file set. It stamps `(mtime, len)` BEFORE the read, so a file rewritten while it was being read reads as changed rather than as current. Recording is free when nobody is asking: it pushes only into frames a `ConfigInputRecorder` opened, and each frame dedups by path
- `ConfigInputRecorder::start()` / `.finish()` — the RAII frame around a derivation; every `record_config_input` between them lands in the returned `ConfigInputs`. Frames nest, so an inner recorder (module resolution inside a tick) does not steal an outer one's entries
- `ConfigInputs::unchanged()` — re-stat every recorded entry and answer whether all of them still hold their recorded `(mtime, len)`. An EMPTY set answers `false` on purpose: a derivation that recorded nothing has nothing that could ever report it stale, and reusing it would be reuse forever
- `daemon::tick_cache::TickCache` (`crates/cfgd-core/src/daemon/tick_cache.rs`) — the daemon's holder built on the above, and the only consumer so far: one derivation of config + profile + composition + registry per CHANGE rather than per tick, a module resolution bounded by the same fingerprint plus a 30s ceiling, the state store opened once and lent behind its own lock (a `rusqlite::Connection` is `Send` but not `Sync`), and one `InstalledEnumerations` lent to every tick's `PackageContext`. A second long-lived holder (an MCP session, a watch-mode command) should reach for this shape rather than mint a second fingerprint scheme. Three obligations come with holding a derivation across ticks, and a new holder inherits all three: the stored result is DISCARDED when an invalidation landed while it was in flight (the epoch is compared under the slot lock, so no window exists between the compare and the store); anything the derivation SAID once per tick is carried on the held object and re-stated by every reusing tick (`CachedConfig::advisories_to_restate`), because a still-broken source that stops being reported looks like one that got fixed; and every lend of the held connection re-derives `file_identity` on the path it was opened from, because cfgd's own legacy-state-dir migration renames that file. The fingerprint is `(mtime, len)` and for inputs read out of the SOURCE cache it stands alone — nothing watches those checkouts — so the sync tick invalidates outright rather than trusting a stat to notice what it just rewrote

## Snapshot normalizers

Plain `cfgd_core::*` exports from `util/paths.rs` (not feature-gated) that make a captured render host-stable before it is compared against a golden. Every snapshot test reaches them through `normalize_for_snapshot`; call one directly only when a capture needs a single fold.

- `normalize_for_snapshot(captured, &[(path, label)])` — the composed entry point: folds `\`→`/`, CRLF→LF, and substitutes each `path` with its `label`
- `normalize_cfgd_version(s, version)` — substitute the EXACT running crate version with `<VERSION>`; a wrong version still fails to match, so real version bugs are not masked
- `normalize_snapshot_durations(raw)` — replace every ` (N.Ns)` elapsed-time suffix with ` (XXs)`. The renderer formats durations as `{:.1}s`, so the span is digits, one dot, exactly one digit, `s`, `)`; anything else in parentheses (a package version, an exit code, a byte size) is left alone. Shared by `tests/apply_snapshots.rs` and the backup-run goldens — never re-implement the scan, or two suites disagree about which parenthesised values are timing

## Test guards

Reached via `cfgd_core::test_helpers::*` (the `test_helpers` module is gated behind the `test-helpers` Cargo feature, enabled in dev/test builds — not bare `cfgd_core::*` like the `util/` helpers above). Pair every consumer with `serial_test::serial` because env-var mutation is process-global.

- `BootstrappedPathDirsGuard::capture()` / `::capture_and_clear()` — RAII snapshot+restore of the process-global bootstrapped-PATH registry. REQUIRED in any fixture that drives a package-manager bootstrap: the registry is never cleared, so a fixture registering a real host directory changes what every later test in the binary can resolve, and only on hosts where that directory exists (registering `/opt/homebrew/bin` made an empty-`PATH` "git is missing" test pass on Linux and fail on macOS). Use `capture_and_clear` in a test asserting a "command not found" branch — emptying `PATH` is not sufficient, because the registry is searched after it
- `path_env_read_guard()` / `path_env_mutation_guard()` — the two halves of `PATH_ENV_LOCK`, a `Mutex`+`Condvar` gate over the process-global `PATH` (not an `RwLock`: a reader may join readers already inside, which a write-preferring `RwLock` refuses and which deadlocked a lane worker against a queued writer). A test that mutates `PATH` (usually emptying it to drive a "command not found" branch) takes the WRITE guard, declared before the `EnvVarGuard` so it drops last and brackets the whole window. Everything that READS `PATH` takes the read guard: `reconciler::scripts::execute_script`, `output::process::run_command`, `util::process::command_output_with_timeout`, and the `git_cmd_*` factories take it automatically, and a test asserting a *successful* `command_path` / `command_available` / `require_tool` resolution takes it by hand. A test asserting a resolution FAILS needs no guard — an empty `PATH` cannot turn a miss into a hit. `serial_test::serial` cannot substitute: it only excludes other serial tests, never the non-serial reader majority. Never spawn or resolve while holding the write guard — same-thread read-after-write is still `debug_assert`ed against and still deadlocks
- `await_queued_path_writer(timeout)` — blocks until a thread is waiting to take `path_env_mutation_guard()`'s exclusive side, answering `false` if none arrives within `timeout`. The observable a concurrency test needs to reach "a writer is queued" without a sleep standing in for it; pairs with `path_env_read_guard()` in a test proving a queued writer does not shut out a reader already joined
- `await_blocking_source_acquire(timeout)` in `util/apply_lock.rs` — the same observable for `acquire_source_lock`'s blocking arm: it answers `true` once a thread has entered the contended acquire and is waiting on the holder. `#[cfg(test)]` inside cfgd-core, so only cfgd-core's own tests reach it. It exists because the `on_wait` callback fires BEFORE the acquire and so proves only that a wait was announced: a test that releases on that signal alone passes with the blocking arm mutated to `Refuse`, since the second try then lands on a free lock. Wait on this instead, and the holder does not release until the contender is genuinely blocked. `timeout` is a deadlock escape, never a timing assertion — assert on the returned bool
- `CommandPathMemoTtlGuard::never_expires()` / `::always_expired()` / `::pinned(ttl)` — RAII pin of the `command_path` memo's 30s TTL, restored on drop. Any test whose claim is that a memoized answer STILL STANDS pins it out of reach, and any test whose claim is that expiry retires one pins it to zero; without the pin both are assertions about how long two adjacent statements took on a loaded runner, which is the exact shape this repo bans (`ConcurrencyWitness` exists for the same reason). Pinning needs no serialization of its own — a longer TTL only lets another test's entries live longer and a zero TTL only makes them recompute, and neither can change the ANSWER a concurrent test reads
- `AvailableVersionMemoTtlGuard::never_expires()` / `::always_expired()` / `::pinned(ttl)` — the same RAII pin over the available-version memo's 30s ceiling (`providers/available.rs`). Pair every use with `#[serial_test::serial(available_version_memo)]`: the pin is process-global and every test that reads this memo asserts on a COUNT of version queries, so a concurrent zero pin makes another test's memoized offer recompute and changes exactly what that test measures. `StubPackageManager::version_query_counter()` is the count itself — taken BEFORE the stub is handed to a resolver, since a `&dyn PackageManager` cannot be read back for it
- `AvailabilityMemoTtlGuard::never_expires()` / `::always_expired()` / `::pinned(ttl)` — RAII pin of the provider-AVAILABILITY sweep's 30s ceiling (`ProviderRegistry`'s memo of which providers are on the machine at all — the sibling of the enumeration memo, which is what a manager HAS). The ceiling exists for the holder that outlives one run: the daemon now keeps ONE registry across ticks, and a generation-only memo would answer "not installed" for the rest of the process's life about a manager a human installed by hand a minute after startup. Pair every use with the UNNAMED `#[serial_test::serial]`, the group the sweep's own count tests already share — a named group would not exclude them
- `GitRefreshWindowGuard::never_expires()` / `::always_expired()` / `::pinned(ttl)` — RAII pin of the module git-cache refresh window (`modules/git.rs`), inside which ONE `git fetch` of a repository serves every later ask for it in the same run. A test that drives two fetches of one fixture repository and expects the second to really transfer (a tag pushed upstream in between) pins `always_expired`; a test whose claim is that one transfer served both pins `never_expires`. The pin SERIALIZES ITSELF — constructing a guard takes a process-global mutex held until it drops — so no call site needs an attribute and no PINNING test can forget one. It excludes pins and only pins: a test that fetches without pinning reads whatever pin is live, so a `never_expires` held elsewhere can spare it a transfer it was counting on. A test whose claim turns on whether a transfer happened must pin, and a test that asserts the pin lock is FREE is asserting about the rest of the suite rather than about its own subject. Per-test temp directories keep two tests from sharing a key in the refresh MAP, but the pin is a single process-global atomic and every test that reads this window asserts on whether a transfer HAPPENED, which is exactly what the pin decides: a concurrent `always_expired` inside a `never_expires` test opens the window to zero and its second fetch reaches for an upstream the fixture has deleted. It cannot use `AvailableVersionMemoTtlGuard`'s named-group answer because its users also need the UNNAMED group for `CFGD_ALLOW_LOCAL_SOURCES`, and `serial_test` accepts only ident keys, so "default group AND a named one" is inexpressible. Unlike `CommandPathMemoTtlGuard`, whose users assert on an ANSWER a pin cannot change
- `measured_in_a_stable_generation(measure)` — run `measure` inside a window in which nothing else moved the process-wide `command_resolution_generation()`, retrying with a fresh call until it gets one. REQUIRED by every memo-hit claim ("the sweep ran once", "the memoized miss still stands"), because any test in the binary that runs a mock install or a lifecycle script invalidates every memo in the process — without it the assertion is not wrong, it is unmeasurable, and it fails at random on a loaded runner. `serial_test::serial` cannot substitute: it excludes only other serial tests, not the parallel majority. The closure must be re-runnable — build the registry, counters and probe files it observes INSIDE it, so a retry measures a fresh subject rather than one an abandoned attempt already warmed
- `captured_text(&buf)` — the ONE read of a `Printer::for_test*` capture buffer, returning it ANSI-stripped. Colour itself is no longer ambient: every capture constructor pins `colors: false` (see `Printer::for_test_with_theme_colored`, the single exception), so a buffer is unstyled BY CONSTRUCTION rather than because this function strips it. Keep using it anyway for any assertion about TEXT — the colour-ON constructor really does emit escapes, an attribute-carrying slot emits SGR even with colour off (NO_COLOR governs colour only per no-color.org), and a subject may carry foreign escapes of its own. Three failure shapes, all observed on the raw buffer while colour was ambient: `contains("module:vim-config")` breaks on the escape between the owner token's two styled halves, `ends_with(path)` breaks on the trailing reset, and every negative `!contains("✓ …")` passes VACUOUSLY once styling is on — it stops guarding anything without ever going red. Reached through the same name from the daemon test harness (`super::harness::captured_text`) and from `cli::tests`'s `TestHarness::output`, which strips for all of its own assertions. The only tests that read the buffer raw are the ones asserting ON the escapes
- `Printer::for_test_split_streams(verbosity)` — the split-stream capture, returning `(printer, stdout, stderr)` as two SEPARATE buffers, the relationship the sinks have in production. The one constructor that can state a stdout-purity claim directly: a merged capture makes the test filter status glyphs back out of the data channel, and then the filter, not the printer, decides what counted as stdout. Reach for it wherever the claim is about which STREAM carried a line (`cmd_deploy`'s pipe-to-kubectl stdout); every other question keeps the merged constructors
- `Printer::for_test_with_theme_colored(theme, verbosity)` — the ONE capture constructor whose buffer carries ANSI, for a test whose subject IS the escapes a theme emits. Every other `for_test*` yields an unstyled buffer whatever the terminal or another thread says. To assert the colour DECISION rather than a rendered escape, call `output::printer::colors_must_be_disabled(&format)` and render nothing
- **The three live-region capture constructors, and the question each one can answer.** They share `live_capture`'s `Printer` shape and differ only in where indicatif draws, so reaching for the wrong one does not fail — it answers a different question, silently. That is not hypothetical: a row's line left on the terminal after the region closed (an action standing in the scrollback twice, once committed and once as a truncated live paint) passed every "commits exactly once" test in the suite, because neither of the first two surfaces can see a paint that was never taken back
  - `Printer::for_test_live_scrollback()` — indicatif draws to a HIDDEN target, so the buffer holds ONLY what was committed permanently and none of the region's repaints. Reach for it to assert what a concurrent apply LEAVES BEHIND: commit order, and that a row is committed exactly once. Blind to the live region by construction
  - `Printer::for_test_with_live_bars()` — indicatif draws into the SAME buffer the sink writes to (`RecordingTerm`), so the buffer is every paint in the order it was made. Reach for it to assert on the region ITSELF (read from its last paint), on interleaving/garbling between the two writers, and on indicatif's own draw ORDER — the only proof that an `insert_after` landed where it was asked to. It cannot answer "how many lines are on screen": a row painted forty times appears forty times, so one paint too many is indistinguishable from one repaint too many
  - `Printer::for_test_live_terminal(rows, cols)` — indicatif draws onto an EMULATED SCREEN (a `LiveScreen`, the `output/`-owned wrapper over indicatif's vt100 `InMemoryTerm`), with the printer's sink writing to the same screen the way stderr carries both in production. Cursor moves and line clears are executed, so `LiveScreen::contents()` is what the terminal is LEFT HOLDING. The ONLY surface that can see a line the region drew and never erased — reach for it for any claim about what survives the region, and note it reads the visible SCREEN, so a region taller than `rows` loses evidence off the top and a bare `!contains` assertion over it would go vacuous. `#[cfg(test)]` inside cfgd-core: its `in_memory` feature is a dev-dependency, so no shipped binary compiles it and no other crate's tests can reach it
- `test_printer()` — a bare Quiet `Printer` for a fixture that drives a command but asserts nothing about its output. Built from `Printer::for_test().0`, NEVER from `Printer::new`: the production constructor inherits the invoking terminal, so under a pty its printer reports both a live region and a human at stdin, and a command reaching an unanswered confirmation prompt BLOCKS for the remainder of the run rather than refusing. A hang is worse than a mismatch — no harness reports it as a failure. The same rule covers every test-side construction: reach for a `for_test*` constructor, and leave `Printer::new` / `Printer::with_format` (which now takes an explicit `ColorChoice`) to production entry points and to the `null_lib_printer`-style suppressed sinks that production itself builds
- `EnvVarGuard::set(key, value)` / `EnvVarGuard::unset(key)` — RAII env-var save/restore (re-exported via `cfgd_core::test_helpers::EnvVarGuard`); captures prior value on construction, restores (or removes if no prior) on drop, even on panic
- `with_test_env_var(var, value, f)` — scoped env-var override; calls `f` with the var set to `Some(v)` or removed for `None`, then restores the prior value
- `spawn_blocking_with_test_home(f)` — `tokio::task::spawn_blocking` that captures the caller's test-home thread-local and re-installs it inside the spawned closure (plain `cfgd_core::*` export, NOT feature-gated — it's a no-op read in production). REQUIRED for every blocking dispatch whose closure may resolve `~`/`$HOME`; never pair a raw `spawn_blocking` with a hand-rolled `test_home_override()` capture
- `ConcurrencyWitness` + `MockPackageManager::with_concurrency_witness(w)` — the observation that two lanes really did overlap: the mock records the peak number of `install()` calls in flight, so a concurrency test asserts `witness.peak() == 3` instead of asserting that a wall-clock elapsed under `delay * 2`. A timing bound is what makes a concurrency test flake under a loaded suite (an overlap-proving run failed at 408.9ms against a 400ms bound); the witness proves the same claim with no clock in it
- `ProbePath::containing(&[names])` — a `PATH` of one temp directory holding exactly the named executables, for a test asserting what a `command_available` probe resolves. Unix-only (the probes are `/bin/sh` no-ops; Windows resolves by `PATHEXT`), and paired with `path_env_mutation_guard()` declared BEFORE it plus `serial_test::serial`. It exists because an `is_available()` test comparing the provider's answer to `command_available("<tool>")` restates the implementation: both sides move together, so it passes on every host and keeps passing when the probed name is misspelled. Assert the negative under an empty `PATH` (with `BootstrappedPathDirsGuard::capture_and_clear()`, since the registry is searched after `PATH`) and the positive under a `ProbePath`, one binary at a time where a provider accepts several — `nix-env` or `nix`, `kwriteconfig6` or `kwriteconfig5` — so dropping one arm cannot hide behind a host that carries both
- `CosignTestShim::install()` / `CosignTestShim::builder()...install()` — consolidated fake-cosign shim (Unix-only); writes a `/bin/sh` script under `CFGD_COSIGN_BIN` with builder-configured argv logging (`with_argv_logging`), keygen-mode key-pair writes on `generate-key-pair` (`with_keygen`), exit code (`with_exit`), and canned stderr (`with_stderr`). Captures + restores prior `CFGD_COSIGN_BIN` / `CFGD_FAKE_COSIGN_LOG` on drop. Replaces the per-file `CosignShimGuard` / `CosignShim` / `CosignKeygenShim` duplicates in `oci/sign/tests.rs`, `upgrade/tests.rs`, and `cli/module/tests.rs`

## Upgrade

- `cleanup_old_binary()` — remove `.exe.old` left by Windows rename-dance self-upgrade; no-op on Unix. Called from `main.rs` on startup (lives in `upgrade.rs`, not `util/`)

## What NOT to do

- Don't create new utility files outside `cfgd-core/src/util/`. Shared functions go in the existing topic file that matches the helper's domain.
- Don't add the same helper as a sibling of an existing topic file. Pick the existing topic.
- Don't create a brand-new topic file unless the helper genuinely doesn't fit any existing one — adding three string-validation functions doesn't justify a new file when `strings.rs` exists.
- Don't duplicate a function that already exists. Search the catalog above first.
- Don't create local timestamp/hash/command-check wrappers — use the shared ones above.
